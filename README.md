# Contextual Bandit Hybrid Bit-Semantic Transmission Selection for UAVs

Machine Learning (25SC2107E) course project. A UAV must decide, for every task, whether to send **exact bits**, the **semantic meaning**, or a **compressed semantic** version. The best choice depends on channel quality, task urgency, delay budget and required quality. We learn this decision online with contextual bandits (LinUCB, Thompson Sampling) and compare against baselines and a DQN.

## Quick start
```bash
pip install -r requirements.txt
python -m pytest -q tests          # 9 sanity tests
python run_all.py --quick          # smoke test, 1-2 min (overwrites results/ with quick numbers)
python run_all.py                  # full reproduction, ~8 min, writes results/
```
**Google Colab:** open `notebooks/run_in_colab.ipynb`, upload the repo zip (or `git clone` your GitHub repo) and run the cells. No GPU or deep-learning framework is needed; everything is NumPy.

## Send a message through the system
Type a message: the program analyses it (task type, urgency, deadline, required quality, key units), reads the channel quality, lets the trained LinUCB policy choose **bit / semantic / compressed semantic**, simulates the transmission and reports the outcome.
```bash
python send_message.py "URGENT: obstacle detected ahead, reduce altitude to 40 meters immediately" --snr 12 --compare
python send_message.py --interactive            # type messages one after another
python send_message.py --file examples/messages.txt --snr random
python run_demo.py                              # 16 messages x 4 channel qualities + policy comparison
```
Useful options: `--snr <dB>|random`, `--policy linucb|bit|semantic|compressed|threshold`, `--compare`, and overrides `--type`, `--urgency`, `--deadline`. The trained policy is stored in `models/linucb_policy.json` (retrained automatically if missing).

How the modes work on text: *bit* sends the exact bytes (arrives intact or is lost); *semantic* sends only the key units (numbers, commands, entities); *compressed semantic* sends the most important ~80% of key units, dictionary-coded. Quality = fraction of key units that reach the receiver; success needs quality >= requirement and latency <= deadline. The channel and cost model are the same functions the policy was trained on. The semantic codec is a transparent rule-based stand-in, not a trained neural codec.

**Message-level check** (16 example messages x 300 random channel draws): learned policy reward +0.833 (success 77%, energy 0.88) vs always-bit +0.867 (success 80%, energy 1.00), oracle +0.941. On this small hand-written set the learned policy is on par with always-bit and uses less energy; it demonstrates the end-to-end pipeline and is not evidence of superiority.

## Dataset details
There is **no external dataset**. Tasks and channel conditions are generated by a simulator (`uav_bandit/environment.py`). All parameters are hand-chosen modelling assumptions, not measurements:
- Channel: line-of-sight with probability 0.6 (SNR uniform 15-30 dB), otherwise non-line-of-sight (-5 to 15 dB).
- Tasks: 3 types (image, sensor reading, control command) x 3 urgency classes (routine, priority, emergency), each with a deadline range and a minimum-quality requirement.
- Modes: bit succeeds with probability rising in SNR (all-or-nothing); semantic and compressed-semantic quality are smooth functions of SNR (compressed has a lower ceiling but is more resilient at low SNR). Latency/energy: bit 0.30 s / 1.00, semantic 0.60 s / 0.60, compressed 0.45 s / 0.35.
- Reward: `+5` if quality >= requirement and latency <= deadline, else `-3`; minus urgency weight (1, 2, 4) x latency; minus energy weight (default 2) x energy.
- Setting B adds a battery budget of 100 energy units per 200-task episode; an empty battery makes transmission fail.

## Method
- **Context**: 13 engineered features (SNR, deadline, quality requirement, urgency one-hot, and "margin"/"slack" features that use the known cost model to express how far each mode is above/below the quality requirement and deadline). Setting B adds battery fraction and time left.
- **Learners**: LinUCB, linear Thompson Sampling, contextual epsilon-greedy, and a DQN (NumPy MLP 64-64, replay buffer, target network).
- **Baselines**: always-bit, always-semantic, always-compressed, random, hand-written SNR threshold rule.
- **Oracle**: best expected mode per task (upper bound). Regret = oracle expected reward minus chosen mode's expected reward.
- **Protocol**: hyper-parameters tuned on 3 held-out seeds (100-102); results on seeds 0-9 (setting A) and 0-4 (setting B). Chosen: alpha=1.0, v=0.6, eps=0.02, DQN lr=0.003, gamma=0.0.

## Results (setting A: independent tasks, 6,000 tasks, 10 seeds, oracle average reward = 0.696)
| Method | Avg reward (mean ± sd) | Cumulative regret | Success rate | Avg energy |
|---|---|---|---|---|
| Always bit | 0.423 ± 0.053 | 1642 | 76.5% | 1.00 |
| Always semantic | -3.534 ± 0.068 | 25401 | 25.8% | 0.60 |
| Always compressed | -3.219 ± 0.050 | 23513 | 19.1% | 0.35 |
| Random | -2.095 ± 0.035 | 16888 | 40.7% | 0.65 |
| Threshold rule | -0.822 ± 0.030 | 9208 | 58.4% | 0.79 |
| Eps-greedy (contextual) | 0.442 ± 0.081 | 1611 | 75.5% | 0.92 |
| LinUCB | 0.507 ± 0.053 | 1206 | 76.0% | 0.91 |
| Thompson Sampling | 0.503 ± 0.073 | 1299 | 76.1% | 0.92 |
| DQN | -0.082 ± 0.049 | 4652 | 66.8% | 0.77 |

- LinUCB has 27% less cumulative regret than always-bit, lower in 10/10 seeds (paired t = -3.83), at the same success rate and about 9% less energy.
- The learners recover roughly 40% of the headroom between the best fixed policy and the oracle within 6,000 tasks. The gain grows as energy becomes scarcer (`results/fig_sensitivity.png`); when energy is cheap, always-bit is nearly optimal.
- The hand-written threshold rule is worse than always-bit. Epsilon-greedy shows no significant gain.
- DQN needs far more data: its total regret is about 3.9x LinUCB's over 6,000 tasks. With 20,000 tasks its steady-state regret per task (0.165 ± 0.015) matches the bandits' (LinUCB 0.185 ± 0.061; always-bit 0.270); the gap is within seed-to-seed spread.

DQN is best here (also at battery budgets 60 and 140). A discount factor of 0 scored best, so the advantage appears to come from using battery state with a nonlinear model, not from long-horizon planning; this is a hypothesis, not something we isolated.

## Limitations (please read)
- The simulator is synthetic; its numbers are assumptions. Conclusions are about the simulated environment.
- The engineered features use knowledge of the simulator's cost model; a real system would have to estimate it. Without them LinUCB falls back to always-bit.
- Semantic quality in the simulator uses parametric curves; in the message demo it is a rule-based key-unit codec. Neither is a trained neural semantic codec, and message quality is measured against the analyzer's own key-unit list.
- The default energy weight (2.0) was chosen after observing that at 1.0 the best fixed policy is within about 6% of the oracle; the sensitivity study reports 0.5-4.
- DQN is a NumPy implementation with light tuning; 100-episode budget in setting B; 5 seeds there.
